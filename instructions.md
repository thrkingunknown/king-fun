## 1. Mission and product boundaries

Build an original, mobile-first, browser-based party-game portal with 27 selectable local-play games: the four original games plus the 23 additional games documented in `docs/party-arcade-game-specs.md`. The four user-supplied gameplay recordings are the interaction/animation reference and are reviewed in [`docs/gameplay-reference.md`](docs/gameplay-reference.md):

1. **Imposter** — local pass-and-play social deduction with private, color-coded role cards, press-and-hold 3D reveal, explicit phone handoff, clue/hint, discussion, timer, voting, and result flow. The supplied Mystery Who local report is authoritative for documented local rules; its online-mode sections are not in scope. The complete report is archived at [`docs/references/mystery-who-full-report.md`](docs/references/mystery-who-full-report.md), with the local extraction at [`docs/mystery-who-local-reference.md`](docs/mystery-who-local-reference.md).
2. **GuessUp** — pack/deck browser, editable teams, a short ready countdown, a large readable charades card, timed Correct/Pass play, optional sensor shortcuts, scoring, team handoff, and result.
3. **Truth or Dare** — selectable prompt packs and All together / Spin the wheel / One at a time modes; animated roulette, explicit Truth/Dare selection, large prompt card, reactions, next/replace/skip/opt-out, and prompt reporting.
4. **I Have Never** — selectable prompt packs and All together / Spin the wheel / One at a time modes; large statement cards, neutral response controls, optional reactions, next prompt, and an independent skip action.

The product is free/open-source, local-first, and original. Do not copy source code, branding, screenshots, illustrations, sounds, exact layouts, proprietary wording, prompt banks, advertisements, premium promotions, locked packs, or upsells from reference applications. The games must be usable offline with curated content. There is no conventional DBMS, mandatory account, cloud-synced game history, or required AI dependency.

Optional AI content generation uses the Gemini → Groq → Cloudflare Workers AI fallback arrangement defined by the user-configurable provider order. Cloudflare Workers AI is always last and always enabled in the UI. The provider settings and public Elysia backend are implemented in source and documented in [`docs/ai-provider-routing.md`](docs/ai-provider-routing.md); deployment, lockfile regeneration, full Bun verification, and live-provider acceptance remain release gates.

## 2. Non-negotiable engineering policies

### 2.1 Bun-only command policy

**Use Bun commands only** to initialize projects, install/update/remove packages, execute project scripts, and launch package CLIs.

Allowed command forms include:

```sh
bun init
bun install
bun add <package>
bun add -d <package>
bun remove <package>
bun update
bun run <script>
bunx <tool> <args>
bun test
bun build <entrypoint> --outdir <directory>
```

Use `bunx` only for packages/tools that have been checked for active maintenance, license, security, platform support, and Bun-runtime compatibility. Prefer locally pinned project dependencies and `bun run <script>` for repeatable project commands.

**Prohibited:** `npm`, `npx`, `pnpm`, `yarn`, Corepack package-manager operations, `node`-based package scripts, and commands copied from documentation that use those tools. Translate vendor examples into Bun equivalents. Do not add a second package manager or generate a second lockfile. Use only `bun.lock`/the lockfile format generated by the approved Bun version. Commit it.

The public application API is implemented as Elysia + Bun in the root `backend/` workspace; the current deployment adapter targets Vercel Bun Functions. Keep it a conventional public API gateway, not a Cloudflare Worker runtime. Do not add Wrangler or a Cloudflare Worker application as the API gateway unless the owner approves a separate architecture change. Cloudflare Workers AI remains an upstream provider called through its REST API by the Elysia service. Verify every deployment tool for Bun compatibility and security before adding it.

Bun is the project package manager and preferred JavaScript/TypeScript runtime for local scripts, tests, and the Elysia backend. The production UI executes in the user's browser. Do not assume every Node-targeted tool is compatible with Bun. Prove compatibility in a small spike before adopting it. If a required vendor tool cannot operate under Bun, do not silently introduce another runtime or package manager: document the blocker and ask the project owner to approve an exception or select a compatible tool.

### 2.2 Future-proofing and lifecycle policy

“Future-proof” means standards-based interfaces, low coupling, replaceable providers, and a disciplined upgrade process. It does not mean predicting future releases.

Before adding or selecting any package, SDK, API, model, CLI, browser API, or deployment service:

- Verify its official documentation, current supported status, release/maintenance activity, compatibility, security advisories, license, and deprecation/EOL notices on the decision date.
- Prefer stable, actively maintained releases. Do not select EOL, deprecated, abandoned, archived, unsupported, preview-only, or end-of-support software for a production dependency.
- Avoid deprecated function calls, lifecycle hooks, configuration shapes, endpoints, and package names even when old examples remain searchable.
- Pin dependency ranges deliberately, commit the Bun lockfile, and update dependencies through reviewed pull requests. Do not leave CI dependent on a floating `latest` tag.
- Add automated checks for vulnerable dependencies, license policy, outdated packages, and deprecation notices where tooling supports them. Review advisories and changelogs; automated status alone is insufficient.
- Record the verification date and official source URL in the architecture decision log or `requirements.md`.
- Wrap provider-specific APIs in adapters. Keep model IDs and endpoint configuration in validated server-side configuration, not scattered through game logic.
- Re-verify all volatile vendor claims before release: model IDs, generation parameters, prices, quotas, free tiers, account requirements, limits, API versions, and deployment commands.

Do not silently replace a user-requested provider/model with another model if it is removed or unavailable. Mark the integration blocked, provide evidence, and request owner approval for a replacement.

### 2.3 UI/UX component and icon libraries are allowed

The project owner explicitly permits additional Bun-managed packages for UI/UX. Contributors MAY use third-party React component libraries, accessible headless primitives, motion/interaction packages, and icon-pack libraries when they materially improve quality or implementation speed. Do not restrict the project to hand-written components or the current dependency list.

Before adding one:
- Verify active maintenance, current releases, security advisories, license, React 19 compatibility, Vite compatibility, Bun install/runtime compatibility, and accessibility documentation.
- Prefer semantic, keyboard-operable components with focus management, reduced-motion support, touch-friendly targets, and documented ARIA behavior.
- Use icon libraries consistently; icons must have accessible labels when interactive and must not replace text where the meaning would be unclear.
- Check tree-shaking and production bundle impact. Avoid introducing multiple overlapping component or icon libraries without a clear reason.
- Install/update/remove packages only with Bun, update the single `bun.lock`, and add tests for any behavior the library owns.
- Keep the game domain independent of UI libraries. A library may render a dialog, menu, sheet, tooltip, or icon, but it must not own role assignment, voting, prompt selection, random outcomes, persistence, or game rules.

### 2.4 Persistence and offline guarantees

- IndexedDB is the durable persistence layer for app state, active sessions/rounds, history, and validated custom packs. `localStorage` may hold only compact, non-secret AI provider ordering/enabled preferences plus the one-time `party-portal-v1` migration source; provider keys, player data, game sessions, and history must never be stored there. The legacy migration source is removed only after a durable IndexedDB snapshot is confirmed.
- Every snapshot has a key, schema version, monotonic revision, update timestamp, and bounded JSON value. Schema changes require an explicit migration and fixtures; reject unknown future versions without overwriting the source.
- Snapshot/session/round/history writes and backup restore are atomic read-write transactions. Normal writers must use revision compare-and-swap. A stale tab must be offered reload/recovery; never silently merge or overwrite another tab's game.
- If IndexedDB is blocked, denied, quota-limited, corrupted, or unavailable, keep the current state in memory where feasible and surface that it is not durable. Disable claims of auto-save, allow a memory backup export, and offer retry. Destructive recovery may force-reset the King-Fun stores only after explicit confirmation.
- Backup import must validate the complete envelope, snapshot schema, bounded state, pack metadata/items, IDs, timestamps, and aggregate size before asking for destructive confirmation. Restore all stores atomically and compare the current revision.
- Service-worker caching is limited to same-origin static assets and the app shell. The Vite build emits a precache manifest for every hashed runtime asset, including lazy game chunks. The worker validates those paths, excludes API/provider and non-GET traffic, caps runtime additions, and deletes only prior `king-fun-shell-*` caches.
- Do not depend on remotely hosted fonts or third-party assets for the offline shell. System font stacks are the default; any future remote dependency requires a local/offline fallback.

### 2.5 Accessibility and presentation quality

- Keep semantic landmarks (`header`, labelled `nav`, one focusable `main`, `footer`), a skip link, visible keyboard focus, accessible form labels, and live status/error announcements.
- Prefer native semantic controls and native `<dialog>` where they provide reliable focus containment/restoration. Screen changes move focus to the main content target; lazy game loads have a status fallback and recoverable error boundary.
- Respect both `prefers-reduced-motion` and the persisted in-app motion preference. Reduced motion must shorten JavaScript-driven transitions as well as suppress CSS animation.
- Keep controls touch-friendly (44 CSS px where practical), preserve safe-area insets and dynamic viewport sizing, support forced-colors/high-contrast modes, and avoid communicating state by color/sound/motion alone.
- The adopted UI stack is documented in [`docs/ui-architecture.md`](docs/ui-architecture.md): Base UI + CVA for button primitives, Lucide React for named icons, accessible switches, CSS-owned shell/home transitions, AutoAnimate for setup list feedback, cmdk for quick navigation, native HTML drag/drop plus keyboard Move up / Move down controls for provider order, and Playwright/axe/Storybook for browser and component validation. Motion, Sonner, and dnd-kit remain installed but are not imported by current app source; do not reintroduce them into the initial route without a measured need, review, and regenerated Bun lockfile.

### 2.6 Correctness, privacy, and security

- All consequential random selection uses an unbiased Web Crypto implementation (`crypto.getRandomValues`) with rejection sampling for bounded integers. Do not use `Math.random()` for player, role, prompt, or winner selection.
- AI output is untrusted input. Validate it against a strict runtime schema, normalize it, apply content policy checks, and reject or fall back to curated content on failure.
- Never expose a project-owned provider secret in browser code, source maps, logs, analytics, or static configuration.
- A user BYOK key may only be sent after explicit consent and only over HTTPS to the public Elysia API, which forwards it to the selected provider for one request. Keep the key in browser session memory only; never persist, export, cache, trace, or analytics-capture it. Redact it from Elysia, host, reverse-proxy, and error logs. The Cloudflare Workers AI deployment token/account ID are server-only secrets.
- Do not log player names, prompts containing personal disclosures, BYOK keys, provider request bodies, or raw model output by default.
- No cloud game-state storage, user profiles, or server-side history without an explicit product-scope change and privacy review.
- Provide skip, replace, and exit controls. No player should be forced to disclose personal information or perform a dare.

## 3. Recommended technical direction

Use the latest stable, officially supported versions at implementation time. Version numbers are intentionally not hard-coded in this document because they must be freshly verified at project creation.

- **Language:** TypeScript with strict compiler options.
- **UI:** React with a Vite-based browser build is the default proposal, subject to current official support and compatibility verification. Keep game rules in framework-independent TypeScript modules.
- **Runtime/tooling:** Bun for package management, scripts, tests, and compatible local CLIs.

Motion, Sonner, and dnd-kit are installed but intentionally not imported into the current application source; keep them out of the initial route unless a measured need justifies deliberate adoption and a regenerated Bun lockfile.
- **State:** explicit game state machines and reducer-style transitions. Avoid a state library until complexity demonstrates a need.
- **Persistence:** IndexedDB for resumable sessions, history, custom packs, and larger content. `localStorage` only for small preferences. Cache API/service worker for offline application assets.
- **Public API:** Elysia + Bun service in root `backend/`, as a separate workspace under the root package manifest and one root Bun lockfile. It validates generation requests, proxies Gemini/Groq BYOK requests, and calls Cloudflare Workers AI with server-side credentials. Do not introduce libraries merely because they are popular. Benchmark the smallest suitable implementation first.

## 5. Core domain contracts

Define and validate contracts before building game screens. Prefer discriminated unions for state machines.

### 5.1 Shared primitives

- `SessionId`, `PlayerId`, `ContentId`, and `PackId`: branded opaque stable IDs, not array indexes.
- `GameSession`: schema version, ID, game ID, status, player roster, creation/update times, and a same-game snapshot.
- `GameSnapshot`: game-specific discriminated phase, schema version, monotonic revision, and bounded JSON state. A restored snapshot never redraws already committed outcomes.
- `ContentItem`: stable ID, game, pack, locale, category, kind, text, tags, suitability, and explicit source/license/creator provenance.
- `ContentPack`: versioned metadata and unique stable content references.
- `GameAction`: typed session/player/content command carrying an expected revision where applicable. Runtime parsing rejects invalid shapes before reducers handle actions.

Do not store secrets or unnecessary personal details in these objects.

### 5.2 Imposter

Model setup, private role distribution, reveal/pass device, clue/discussion, voting, tie resolution, result, and next-round phases explicitly. A round stores the selected word and every player's assigned role before reveal begins. Never regenerate roles on resume. The reveal UX must prevent a later player from seeing the previous player's card accidentally (cover screen, explicit handoff, and optional pass acknowledgement). Ensure the number of roles is valid for the roster. Support a configurable ruleset; document defaults rather than burying assumptions in UI code.

### 5.2.1 Mystery Who local rules (mandatory)

Use the complete user-supplied Mystery Who gameplay report, archived at `docs/references/mystery-who-full-report.md`, as the local-mode rules reference; its online multiplayer sections are excluded. Use `docs/mystery-who-local-reference.md` for the extracted local contract. Implement its three modes and role boundaries, not generic social-deduction assumptions.

- **Classic:** Civilians and Mystics; no Mr. White.
- **Mystics:** configurable ordinary Mystic count plus exactly one Mr. White.
- **Chaos:** randomized 1–3 Mystics and 45% Mr. White chance with at least four players; always preserve at least one Civilian.
- Player range 3–20; Mystic count bands 3–5:1, 6–10:2, 11–15:3, 16–20:4.
- Civilian receives category + word; Mystic receives category + optional hint(s); Mr. White receives category only.
- Private reveal begins immediately on pointer/key press (no artificial hold delay), conceals on release/cancel/focus loss, and uses explicit gated handoff.
- Discussion timer is optional, discussion-only, 15–600 seconds in 15-second steps, default 180 seconds and off by default.
- Voting is on by default; each player submits exactly the ordinary Mystic count as unique targets, may self-vote, or skip. Validate turn order and targets.
- After all ballots, Mr. White gets one final exact-word guess if they receive at least half of all submitted selections, rounded up. Normalize by trim/lowercase/whitespace collapse.
- Results expose word, category, roles, tally, hints and Mr. White result; hidden-voter mode hides voter identities.
- Support 30 built-in categories, combined multi-category selection, local custom packs, `word | hint1 | ...` lines, JSON/TXT import/export, and normalized last-10 word exclusion.
- Troll Mode effects and civilian/mystic elimination/win rules, plus detailed tie/no-vote victory transitions, are not described in the report. Do not invent them; keep them blocked pending a more detailed authoritative specification.
- The report names 30 built-in categories and reports 60 words/category (1,800 total) with 20 hints/entry. Current King-Fun seed content has 1,800 answers across 30 categories (60/category), with four shared category-safe hints per answer. Word-specific expansion toward 20 hints/answer remains a content-authoring task; only add semantically relevant, human-reviewed clues, never generic filler.

No online rooms, host migration, matchmaking, remote private-role delivery, online voting, chat, or voice are part of this scope. The report's online mode is explicitly ignored.

### 5.3 GuessUp

Represent team, round owner, current card, round deadline, correct/pass counts, and completion state. Use a monotonic deadline when available; persist a wall-clock deadline and reconcile on resume. Sensor tilt is optional, permission-gated, and never the only input method. Always show accessible Correct and Pass buttons. Prevent duplicate score increments from rapid repeated events.

### 5.4 Truth or Dare

Separate player selection from wheel animation. Choose the selected player first using the domain RNG, then animate the wheel to that exact result. Do not let animation frame timing determine the selection. Record the resolved selection in state before starting the visual animation so reloads resume correctly. Let the player choose truth/dare according to the chosen ruleset; include skip/replace and opt-out affordances.

### 5.5 I Have Never

Support group rounds and multiple response conventions (for example fingers, points, or simple reactions) without assuming alcohol. Store only the minimum round state needed to resume. Make prompt suitability visible before starting a pack. Provide a content report/skip mechanism without collecting sensitive details.

## 6. Random selection and no-repeat behavior

Implement one reviewed random module. Its production source must use `crypto.getRandomValues`; its test source must be injectable/deterministic. Never use `Math.random()` for player, role, category, prompt, or wheel-winner selection.

For Mystery Who, keep a persistent rolling history of the **10 most recently selected Imposter words** across categories. Compare both stable content IDs and normalized text (trim, lowercase, collapse whitespace). Keep the Imposter-specific last-10 restriction even while category-aware generation queues are added. If the eligible selection is exhausted, stop and report it; never silently relax the rule.

For player selection, if `n >= 4`, use the owner-defined rolling exclusion window:

```ts
playerWindow(n) = Math.max(1, Math.round((n / 2) - 1))
```

For fewer than four eligible players, this adaptive window is zero. Store recent player IDs separately per game, filter them from the eligible set, and sample uniformly from the remaining players with the Web Crypto selector. Do not apply this player-selection policy to role assignment or other unrelated random outcomes.

For category selection, let `k` be the number of distinct categories selected for the current game setup:

```ts
categoryWindow(k) =
  k < 2 ? 0 :
  k < 4 ? 1 :
  Math.max(1, Math.round((k / 2) - 1))
```

Maintain one recent-category FIFO per game. Use the queue only after a category is committed, not while browsing. If no category is eligible because the selected set changed, prune obsolete category IDs; if needed, relax the oldest entry first.

For content, keep independent queues keyed by `gameId:categoryId:itemKind:locale`. Never share a queue across games or between Truth and Dare. Initial capacities: Imposter 10 (plus the source-parity last-10 constraint), GuessUp 20, Truth 20, Dare 20, and I Have Never 20. Also keep a per-round seen set so an item cannot repeat in the same round after it ages out of the rolling queue. Use stable IDs, canonicalized text, and a conservative near-duplicate check. The LLM receives only the matching game's/category's recent items and must be instructed to avoid exact duplicates and close paraphrases; the model instruction is not the enforcement boundary.

Ask providers for five new items per batch. Assign IDs/fingerprints outside the model, validate the complete batch, and only append accepted items to the correct queue. Invalid or duplicate results never advance history. If no eligible curated/generated content remains, show an explicit exhausted state instead of silently repeating. Full formula, key, and retry details live in [`docs/ai-provider-routing.md`](docs/ai-provider-routing.md).

For a uniformly sampled integer in `[0, n)`, the current implementation derives a uniform 53-bit integer from two Web Crypto `Uint32Array` words, then uses rejection sampling:

1. Validate `n` is a positive safe integer (`n <= Number.MAX_SAFE_INTEGER`).
2. Define the source range as `2^53` and compute `limit = 2^53 - (2^53 mod n)`.
3. Draw a 53-bit candidate; reject it when it is greater than or equal to `limit`.
4. Return `candidate mod n`.

This supports all positive safe-integer bounds without modulo bias. Use Fisher–Yates with that bounded-integer helper. The deterministic source seam is internal to the random module and is used only by tests; production selection functions do not accept caller-provided RNGs.

Persist chosen outcomes in the game snapshot. A reload must not re-roll a player, word, role, category, or wheel outcome.

## 7. Local persistence, recovery, and offline support

No conventional DBMS. Use IndexedDB for game sessions, history, custom packs, and content metadata. Use `localStorage` only for compact preferences such as selected theme, sound/motion preference, and last-opened game. Keep static app assets in the Cache API through a service worker.

Requirements:

- Every stored record has a schema version and stable ID.
- Persist state after every committed action or in a short bounded debounce where loss is acceptable; define exactly which transitions require synchronous persistence before UI advances.
- Use IndexedDB transactions for atomic updates. Maintain a monotonically increasing revision so stale tabs cannot silently overwrite newer state.
- Use `BroadcastChannel` for cross-tab change notifications. On conflict, reload the latest revision and offer a clear conflict/reopen choice rather than last-write-wins for active sessions.
- Store timestamps and state needed for recovery, but do not store secrets or raw provider keys.
- Add forward migrations and migration tests. If migration fails, preserve the original record, offer export/recovery, and allow a safe reset.
- Handle private browsing, quota exhaustion, eviction, and unavailable storage. Show a clear warning when persistent storage cannot be guaranteed; never claim local persistence is permanent.
- Add user-controlled delete/export for local history and custom packs.
- Do not cache authenticated AI responses, BYOK keys, or sensitive requests in the service worker.
- Offline mode must support core games from bundled/cached content. AI generation is optional and must degrade to curated local packs when unavailable.

## 8. AI provider integration and public backend

The normative provider UI, fallback behavior, queue contract, API request schema, and Elysia backend plan are maintained in [`docs/ai-provider-routing.md`](docs/ai-provider-routing.md). Do not implement a second or conflicting provider design.

### 8.1 Provider list UX

- Default visual order: Gemini (disabled, key required), Groq (disabled, key required), Cloudflare Workers AI (always active, pinned last).
- Gemini/Groq rows have a drag handle, settings icon, and toggle. Without a key, the toggle is disabled/greyed. The settings icon opens a modal to enter, test, replace, or remove the key. A saved key unlocks the switch but does not turn it on.
- Gemini/Groq can be reordered whether enabled or disabled. Provide keyboard Move up/Move down alternatives.
- Cloudflare Workers AI remains the last row, cannot be moved, has no settings icon and no toggle. It is the final remote fallback; local content is the final offline fallback.
- Persist order/enabled preferences locally. BYOK key values stay in session memory and are removed on reload/tab close; never write them into local persistence or backups.

### 8.2 Fallback behavior

At round start, snapshot the enabled provider order. For a generation request, try each configured provider once in that order, always including Cloudflare last. On error, show a concise safe snackbar naming the failed provider, reason class, and next provider. Invalid credentials are marked `Needs attention`; transient failures use bounded cooldown/circuit-breaker logic. Provider changes apply next round, while an explicit key removal immediately excludes that provider. If all remote providers fail, use the relevant local curated queue or show an explicit exhausted state.

### 8.3 Elysia + Bun API service

Use Elysia because it is optimized for Bun and supports the Web Request/Response model. Keep server source under root `backend/`; root `package.json` declares `frontend/` and `backend/` workspaces and the only lockfile is root `bun.lock`. Do not add a nested lockfile or package manager. The public API exposes only health, non-sensitive readiness, and validated content-generation routes. It is not a generic URL proxy.

The service sends Cloudflare Workers AI requests using server-only environment credentials/model configuration. Gemini/Groq BYOK keys are provided in a dedicated HTTPS request header and forwarded for that request only. The backend never persists or logs those keys. Its logs contain only request ID, provider ID, task kind, latency, status class, and safe error code.

The public service must enforce schema/provider allowlists, exact CORS origins, body/output/time/concurrency limits, edge/IP rate limits, global provider budget, circuit breakers, and an emergency disable switch. CORS is not authentication. The service does not store game state or player history and does not introduce a conventional DBMS.

Cloudflare Workers AI itself is called via the official REST API with an Account ID and API token held only on the server. Select the least-privilege token permissions supported by current Cloudflare guidance and re-verify model availability/limits during deployment.

### 8.4 Provider request and validation

Every request identifies a closed task/game/item-kind pair, category ID, locale, suitability, count (five by default), and only the recent queue relevant to that game's category. Do not send player names, roles, votes, private words, or unrelated queue contents. The client never supplies an arbitrary URL or model ID.

Each adapter owns authentication, endpoint, model configuration, request serialization, and response parsing. Model IDs and endpoint versions are volatile: verify official documentation, authentication, structured JSON support, quota, price, context/output limits, and parameter bounds immediately before implementation/release. Do not advertise a provider as free or unlimited.

### 8.5 BYOK and secret handling

The UI must disclose that Gemini/Groq keys transit the public King-Fun Elysia server and then reach the selected provider. Obtain explicit consent before the first BYOK save/use. Keep keys in session memory only. Redact the key header from Elysia request logs, host logs, reverse proxy, traces, and exception payloads. No key is written to localStorage, IndexedDB, Cache API, history, backup, analytics, or telemetry. Clearing/reloading the tab removes the key and returns that provider to the key-required state.

Cloudflare Account ID, API token, model ID, and budget controls are deployment configuration/secrets. They must never ship in Vite environment variables or browser assets.

### 8.6 Output safety and fallback

- Use provider structured-output/schema features only if the currently selected model/API supports them; validate on the server and client regardless.
- Enforce count, length, locale, category, suitability, unique IDs, canonical uniqueness, per-round seen set, and per-category recent queue.
- Reject empty, malformed, duplicate, unsafe, discriminatory, coercive, identifying, or out-of-scope content. Never render generated HTML or scripts.
- Use bounded timeouts/retries; each provider is attempted at most once per request. A cancelled user request stops immediately.
- Safe errors use normalized codes such as `TIMEOUT`, `RATE_LIMITED`, `AUTH_INVALID`, `PROVIDER_UNAVAILABLE`, `INVALID_RESPONSE`, `DUPLICATE_ONLY`, and `BUDGET_EXHAUSTED`. Never display raw upstream payloads.
- Keep curated local content available and use it after remote fallback fails. Do not send player disclosures or game history to AI providers.

## 9. UX and visual system

The four user-supplied gameplay videos define the interaction reference. Read [`docs/gameplay-reference.md`](docs/gameplay-reference.md) before implementing or redesigning any game. Create an original, polished experience rather than copying any reference screen.

- **Shared:** focused mobile-first play surfaces, grouped setup cards/sheets, persistent safe-area-aware primary action, large prompt/role typography, obvious progress/turn ownership, and concise state labels.
- **Imposter:** full-size color-coded role card; 3D hold-to-reveal; immediate conceal-on-release; explicit phone handoff; then verified clue/hint, discussion/timer, vote, and result phases.
- **Truth or Dare:** pack picker; All together / Spin the wheel / One at a time; animated roulette with committed winner; large Truth/Dare selection; prompt card; reactions; next/replace/skip/opt-out and report.
- **GuessUp:** deck browser and selected-pack tray; team setup; configurable duration; 3-2-1 ready countdown; large charades card; Correct/Pass feedback; score/time display; team handoff and result.
- **I Have Never:** pack picker and All together / Spin the wheel / One at a time modes; large statement card; neutral response/reaction controls; progress, independent skip, and next-player flow.

Use color to reinforce game identity, never as the only status/role cue. Animate wheel, role/prompt card, countdown, handoff, score, and result changes with stable dimensions and transform/opacity-first motion. Commit outcomes before animation. Make every action operable with touch and keyboard; tilt, vibration, and sound are optional. Respect `prefers-reduced-motion` and offer immediate/static equivalents. Do not introduce ads, premium packs, upgrade banners, or locked paid content.

## 10. Accessibility, localization, and content design

Target WCAG 2.2 AA (verify criteria and tooling current at implementation). Use semantic controls, appropriate names/labels, logical focus order, keyboard operation, visible focus, sufficient contrast, status announcements, and captions/alternative text for meaningful media. Avoid custom controls where native controls suffice. Do not rely on colour, tilt, audio, or animation alone.

Externalize UI strings and content locale. Avoid concatenating language fragments where word order differs. Ensure dynamic prompts are announced without repeatedly interrupting screen readers. Support large text and zoom/reflow.

All prompts, clues, word lists, and illustrations must be original, licensed, or user-created with rights confirmed. Store content provenance and license metadata. Do not scrape or copy the reference apps' question banks. Include age/suitability categories and an easy pack-selection screen. “Adult” content must be opt-in and age-gated by product policy; never make it the default.

## 11. Performance and resilience

Set measurable budgets after a production baseline is collected on representative devices. Initial suggested targets, to be reviewed with real measurements:

- Keep initial route JavaScript lean; split each game and AI-related code into lazy chunks.
- Avoid loading AI provider SDKs in the browser; all provider traffic should pass through the public Elysia + Bun gateway.
- Keep animation smooth on mid-range Android devices; test under CPU throttling and reduced network conditions.
- Avoid large component libraries, heavy animation runtimes, and large image assets without evidence they are needed.
- Keep curated packs available offline and avoid blocking game start on AI/network availability.
- Handle provider timeout, quota exhaustion, unavailable storage, service-worker update, and malformed content with useful UI states.

Define actual budgets in `requirements.md`/`checklist.md` after a representative production build, not with unsupported blanket promises such as “60 FPS on every phone.”

## Phase 5 AI gateway implementation note — 2026-11-05
